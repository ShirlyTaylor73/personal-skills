# Plan

产出决策完备、自包含、可直接交接执行的短期计划：执行者（可能是换了线程或换了模型的 agent）只读这一份文件就能动手，不需要临场拍板。本 skill 只做规划，不接管后续执行。

## 硬边界

- **只规划，不执行**：不修改任务涉及的源码、文档、配置、数据或 git 状态，不运行有写入或对外副作用的命令。唯一的写操作是把计划写入 `.agents/plans/`（目录不存在时创建，不顺手改 `.gitignore` 等其他文件）。当前目录不可写时，在对话中输出完整计划并说明未落盘的原因。
- **术语与决策只进计划**：澄清中对齐的关键术语、难以逆转且有真实取舍的决策，记录在计划的“约束与决策”一节；需要沉淀到项目长期文档（术语表、决策记录、`AGENTS.md` 等）时，写成实施步骤里的一条，留给执行阶段完成，规划期不改这些文件。
- **范围闸门**：一份计划只覆盖**最多一个 release / 交付周期的短期目标**，或**起步的最小 MVP**。从 0 到 1 的完整产品、跨阶段的大型改造不进入单份计划，按下文“范围判定”处理。
- **≤ 200 行，不写成品**：计划文件总行数（含 frontmatter、标题与空行）硬上限 200 行；小任务通常 40–100 行即可，不凑字数。计划不是成品：不贴完整文件、大段代码、成稿正文或逐行伪代码；只有文字无法消除歧义时，才给数行以内的接口签名、数据结构或格式示意。
- **路径用行内代码**：正文引用文件路径一律写成 `` `src/app.py` ``，不写相对 Markdown 链接——计划里常出现尚未创建或即将改名的文件，链接容易触发文档链接检查失败。

## 流程

### 1. 只读勘察：本地 + 网络

- **本地勘察**：先读与任务直接相关的材料：`AGENTS.md` / `README`、相关文件及其上下游引用、现有检查或测试入口、已有的决策记录与说明文档、`git status`（如适用）。只查必要范围，不通读全部。
- **网络核实**：任务依赖外部库、工具、标准、规范或时效性信息时，用当前环境可用的文档查询或网页搜索工具核实最新资料并记下来源，不凭记忆断言。
- **可查证的事实不问用户**：读文件、配置、历史或公开资料能弄清的，自己查清。
- 记下与用户描述冲突的地方：用户用词与已有概念不一致或含混（例如用户说“账户”，代码里同时有 `Account` 与 `User`）、需求与现状或既有决策矛盾——这些是澄清的必问项。

### 2. 范围判定

勘察后先判断是否超出单周期 / 最小 MVP。出现任一信号即视为超范围：

- 包含多个可独立发布或交付的阶段；
- 横跨多个独立系统面，或存在多组互不依赖的验收目标；
- 删去实现细节后，仍无法在 200 行内说清边界与验收。

超出时不写任何文件，直接在对话中：

- 给出 2–4 个可独立交付的开发周期：每期一句话交付物、依赖顺序、建议先做哪一期及理由；
- 请用户选定当前一期（或调整切分），然后停下等待回复。

用户选定后，只为这一期走后续流程，其余周期在计划的“非目标”里各记一行。

### 3. 逐层拷问澄清

目标是把设计决策树走完：凡是会改变范围、对外行为、接口契约、数据形态、兼容性或不可逆取舍的决策，在落盘前都要有明确结论，不把它们留成执行者的默认假设。

- **按前沿分轮**：每轮只问“前提已确定”且彼此独立的问题（通常 1–4 题）；依赖本轮答案的下游问题留到下一轮。每轮收到答复后，重新检查决策树，展开新出现的分支，直到前沿清空。
- **每题带推荐**：给 2–4 个有意义的互斥选项、推荐项与一句取舍理由，措辞让用户可以只回“按推荐”就通过。
- **用场景压测**：对关键设计构造具体边界场景（空数据、并发、失败重试、旧数据兼容、权限不足等）向用户确认预期行为，而不是抽象地问“要不要处理异常”。
- **点破冲突**：勘察中记下的术语或现状冲突，必须在澄清中让用户确认采用哪个含义或哪个方向。
- **不问的内容**：可查证的事实；不影响外部行为、仅属于内部实现的细节（命名、私有函数拆分等）——这些由你在计划里直接定下。
- **提问方式**：优先使用当前环境可用的交互式提问工具；没有时在对话中列编号问题。**发问后立即结束本轮等待答复**，不得在收到答复前自行假设结论并落盘。
- **提前结束**：用户明确表示“够了 / 其余按推荐”时停止追问，把剩余未决项按推荐写进计划，并标注为“默认假设”。

需求本身已经完全明确时，可以零轮澄清直接落盘。

### 4. 落盘计划

路径：`.agents/plans/YYYY-MM-DD-<slug>.md`（`<slug>` 为简短的小写英文连字符名）。修订同一计划时原地覆写，不追加补丁式段落；同日不同计划重名时加 `-2` 等后缀。语言跟随用户。

文件以极简 frontmatter 开头，只放两个字段：

```yaml
---
scope: 一句话说明本期交付什么
status: draft
---
```

`status` 取值：`draft`（刚写出或修订中）、`approved`（用户明确认可该计划后改为此值）。不添加其他字段。

正文按需选用以下章节，没有实质内容的节直接省略：

1. **目标与非目标**：本期交付结果；明确不做的事，含拆到后续周期的事项。
2. **约束与决策**：从本地或网络资料核实的硬约束、对齐后的术语、澄清敲定的结论（重大取舍附一句理由）、标注出的默认假设。
3. **方案设计**：按子系统、模块、产出物或行为组织，写清对外接口、数据契约或交付物结构的变化、关键流程、边界与失败处理；优先复用已有模块与资料，不臆造本期用不上的机制。
4. **实施步骤**：按模块、子系统或行为分组并按依赖排序，写清每组做什么与注意事项；仅在消除歧义或定位关键入口时标注路径（行内代码），避免逐文件流水账。
5. **验证与验收**：真实存在的检查 / 测试命令，或可逐项核对的验收标准（非工程任务用核对清单表达）；要验证的外部行为与验证位置（优先参考已有做法），以及澄清中确认过的边界场景。
6. **风险与开放问题**：仅在确有外部依赖或残余风险时保留。

写盘后用计数命令（如 `wc -l`）实测总行数，不凭肉眼估算。超过 200 行时，先删实现细节、重复背景和流水账；仍然超限，说明本期范围过大，回到第 2 步与用户收窄或再拆分，不突破上限。

### 5. 交付并停在规划态

回复中给出：计划文件路径、实测总行数、3–5 行核心摘要，以及最值得用户复核的 1–2 个假设或边界。不询问“要不要现在开始执行”，也不自行开始执行。

用户提出修改意见时，原地修订同一份计划（意见本身有歧义就先澄清）；用户明确认可计划时，把 `status` 改为 `approved`；已 `approved` 的计划后续发生实质性修改时，同步把 `status` 改回 `draft`，等待用户重新认可。
